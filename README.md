# Example: Async BDCT with Kafka and PactFlow

This repository is a practical example of asynchronous contract testing using Kafka, Java, AsyncAPI, and PactFlow.

It demonstrates the real workflow behind this pattern:

- the consumer generates a Pact message contract
- the provider publishes its AsyncAPI contract
- PactFlow compares them
- the deployment gate blocks incompatible versions before release

This is not a generic multi-language workshop. The current example is focused on the Java Kafka consumer/provider pair and the bi-directional contract testing flow used in the demo.

## What this example does

The project models a product event flow:

- Consumer: listens for a Kafka `products` event and expects a message with fields such as `id`, `name`, `type`, `version`, `event`, and optional `price`
- Provider: publishes a product lifecycle event on the `products` topic
- Consumer contract: generated as a V4 asynchronous message Pact using the Java consumer test
- Provider contract: defined in `provider-java-kafka/asyncapi.json` and validated with the provider-side test
- PactFlow: stores the published consumer contract and provider contract, and evaluates compatibility through `can-i-deploy`

The key demonstration is that a provider can pass its own tests and still be incompatible with the consumer contract. The deployment gate prevents that incompatible version from being deployed.

## Project structure

- `consumer-java-kafka/` - Kafka consumer example and generated Pact contract
- `provider-java-kafka/` - Kafka provider example, AsyncAPI document, and provider tests
- `bdct-demo.sh` - helper script for local consumer/provider baselines and intentional breakage demo
- `Demo-consumer-side.md` - consumer-side publishing flow
- `Demo-provider-side.md` - provider-side break/gate/recover flow
- `README.md` - project overview and setup

## Requirements

Before running the demo, make sure you have the following installed:

- Docker
- Java 17+
- Python 3
- Git
- A PactFlow tenant with a valid API token and workspace URL
- Optional: Node.js and AsyncAPI CLI if you want to validate the schema manually

You do not need a local `pact` or `pactflow` binary installed in the shell. The example uses Docker to run the Pact CLI, which keeps the setup simple and reproducible:

```bash
pact_cli() {
  docker run --rm \
    -v "$PWD:/work" -w /work \
    -e PACT_BROKER_BASE_URL \
    -e PACT_BROKER_TOKEN \
    pactfoundation/pact-cli:latest "$@"
}
```

## Setup

Set your PactFlow workspace values before running publishing commands:

```bash
export PACT_BROKER_BASE_URL="https://YOUR-TENANT.pactflow.io"
export PACT_BROKER_TOKEN="YOUR_API_TOKEN"
```

Then define the demo identities:

```bash
export DEMO_VERSION="demo-$(date -u +%Y%m%dT%H%M%SZ)"
export CONSUMER="pactflow-example-consumer-java-kafka-V4"
export PROVIDER="pactflow-example-provider-java-kafka"
```

The consumer and provider names must match the generated Pact and the published provider contract exactly.

## Local validation commands

From the repository root, you can run the project-local checks:

```bash
bash bdct-demo.sh consumer
bash bdct-demo.sh provider
bash bdct-demo.sh baseline
bash bdct-demo.sh broken-provider
```

What these do:

- `consumer` - runs the Java consumer test and validates the generated V4 Pact contract
- `provider` - runs the provider schema validation against `asyncapi.json`
- `baseline` - runs both consumer and provider checks together for a known-good local state
- `broken-provider` - intentionally creates a breaking schema change and shows how the provider validation fails

## Consumer side: generate and publish the Pact

The consumer is responsible for expressing the event contract it expects to receive.

The contract is generated by the Java test in `consumer-java-kafka`:

```bash
bash bdct-demo.sh consumer
```

This should produce a contract similar to:

```bash
consumer-java-kafka/build/pacts/pactflow-example-consumer-java-kafka-V4-pactflow-example-provider-java-kafka.json
```

Then publish it to PactFlow:

```bash
pact_cli pact-broker publish \
  "consumer-java-kafka/build/pacts/${CONSUMER}-${PROVIDER}.json" \
  --consumer-app-version "$DEMO_VERSION" \
  --branch bdct-demo
```

This is the consumer-driven contract: the consumer defines the expected payload and publishes the agreement for the provider team to satisfy.

## Provider side: validate and publish AsyncAPI

The provider owns the contract in `provider-java-kafka/asyncapi.json` and validates the produced event payload against it.

Run the provider tests locally:

```bash
bash bdct-demo.sh provider
```

Then capture the result and publish the provider contract together with the test output:

```bash
mkdir -p provider-java-kafka/build/bdct

if bash bdct-demo.sh provider \
  > provider-java-kafka/build/bdct/provider-test.log 2>&1; then
  PROVIDER_TEST_EXIT=0
else
  PROVIDER_TEST_EXIT=$?
fi

pact_cli pactflow publish-provider-contract \
  provider-java-kafka/asyncapi.json \
  --provider "$PROVIDER" \
  --provider-app-version "$DEMO_VERSION" \
  --branch bdct-demo \
  --specification asyncapi \
  --content-type application/json \
  --verification-exit-code "$PROVIDER_TEST_EXIT" \
  --verification-results provider-java-kafka/build/bdct/provider-test.log \
  --verification-results-content-type text/plain \
  --verifier "JUnit5-networknt-json-schema"
```

This upload gives PactFlow both:

- the provider contract itself
- evidence that the provider passed or failed its own verification

## Deployment gate: `can-i-deploy`

The important part of the demo is the deployment decision.

Once the consumer and provider contracts are published, you can check compatibility with the exact versions in play:

```bash
pact_cli pact-broker can-i-deploy \
  --pacticipant "$CONSUMER" --version "$DEMO_VERSION" \
  --pacticipant "$PROVIDER" --version "$DEMO_VERSION" \
  --retry-while-unknown 12 \
  --retry-interval 5
```

This is the gate that prevents unsuitable releases from being deployed. It is especially valuable when a provider passes its own tests but introduces an incompatible contract change.

## Breaking-change demo

The project includes a deliberate breaking-change flow. This shows what happens when the provider changes a contract field that the consumer still expects to be different.

The files involved are:

- `provider-java-kafka/src/main/java/io/pactflow/example/kafka/ProductEvent.java`
- `provider-java-kafka/asyncapi.json`

In the breaking example, the provider renames the payload field from `name` to `productName` while the consumer contract still expects `name`.

The `broken-provider` path demonstrates this mismatch locally and then the deployment gate will block the incompatible provider version in PactFlow.

## Scripts vs manual demo flow

This repository includes both helper scripts and manual step-by-step demo files.

- `bdct-demo.sh` is a convenience wrapper for the local validation flow. It checks the consumer contract generation and the provider contract validation, and it includes an intentional broken-provider scenario to show how a contract mismatch fails locally.
- `Demo-consumer-side.md` and `Demo-provider-side.md` describe the full manual flow, including PactFlow publishing, environment setup, `can-i-deploy`, deployment gating, and recovery after a breaking change.

In practice, the scripts are useful for quick local validation and repeatable demos. The markdown files are the source of truth for understanding what is happening in the demo, because they show the exact values, versions, and publication steps.

This means you can use the scripts to speed up the workflow, but the manual process is still the best way to learn the underlying contract-testing story.

## Summary

This example shows a realistic BDCT-style flow:

1. the consumer defines what it expects
2. the provider validates its own contract against real output
3. both sides publish their contract artifacts
4. PactFlow checks compatibility through `can-i-deploy`
5. incompatible provider versions are blocked before deployment
6. the provider can restore compatibility and pass the gate again

The repository is intentionally designed to make that story easy to demonstrate in front of a customer or during a workshop session.
